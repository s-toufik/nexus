# Homelab security model

> No single wall: layers, each assuming the one before it can fail. Network (who can connect), identity (who you are), authorisation (what you may do), the pod (what a broken process can do), data (what a bad query can see), secrets (where passwords live), and checks that prove it all holds.

## Who are we defending against?
A **threat model** names them, so each control has a reason:
| Threat | Example |
|---|---|
| Someone on the home network | A guest's phone, a compromised smart TV |
| A malicious web page you visit | It tries to make your browser call `https://<domain>/api/...` |
| A compromised or buggy app | A dependency of homelab-ui is backdoored |
| Code the agent writes | A prompt injection makes it run `curl` against the database |
| You, by mistake | `kubectl delete` on the wrong thing, a password in git |
| The internet | Not reachable at all: no port is forwarded on the router |

## The layers
| Layer | Control | Stops | Concept |
|---|---|---|---|
| **Network** | Every port binds to the Tailscale address; nftables drops Kubernetes' ports from the LAN; nothing forwarded on the router | Home network, internet | [[Tailscale]], [[Firewall and nftables]] |
| **Transport** | HTTPS with a real certificate for every web tool | Eavesdropping on the tailnet path (and it's needed for `Secure` cookies) | [[TLS and certificates]] |
| **Identity** | Keycloak: Argon2id hashes, 12+ chars, history 5, lockout after 5 failures; admin console blocked; accounts from the terminal | Password guessing, stolen hash cracking | [[Password hashing]], [[OAuth 2.0 and OpenID Connect]] |
| **Session** | `__Host-` cookie, `Secure`, `SameSite=Lax`, 8 h; identity headers stripped and set by Caddy only | Forged identity, cookie theft across sites | [[Cookies and sessions]], [[Forward authentication]] |
| **Request** | Writes need `X-Homelab-Request: 1`; API paths allow-listed; `read_only` where possible | Cross-site request forgery, reaching admin endpoints | [[CSRF]] |
| **Authorisation** | `admin` role for Kubernetes, Headlamp, Kafka writes, model unload | A normal account doing admin things | [[RBAC]] |
| **Pod** | seccomp `RuntimeDefault`, no privilege escalation, all capabilities dropped, non-root, read-only root FS, no API token unless granted | A compromised process escalating to the node | [[Pod security context]] |
| **Network inside** | NetworkPolicies on agent-toolbox, MCP servers, MCP Inspector, kube-api | Agent code reaching data; lateral movement | [[NetworkPolicy]] |
| **Data** | One role per app with minimal rights; RLS on Tasker; gateway secret checked in the database | One app reading another's data; UI bugs leaking rows | [[PostgreSQL roles and privileges]], [[Row-level security]] |
| **Secrets** | Kubernetes Secrets, encrypted on disk by k3s; generated by `make secrets`; typed at a hidden prompt; never in git, never on a command line | Leaks via git, shell history, `ps` | [[Secrets management]] |
| **Recovery** | Nightly backups outside the cluster, root-only | Data loss, ransomware inside the cluster | [[Backups and restores]] |
| **Proof** | `make validate` before, `make verify` after | Drift: a control you *think* is there but isn't | |

## Why passwords never go on a command line
A command line is visible to every user via `ps`, stays in `~/.bash_history`, and often ends in logs. So `make user-add` asks at a hidden prompt and sends the password on **stdin** to `kcadm.sh` inside the Keycloak pod; `make secret-set` reads the value the same way.

## kube-api: admin power, carefully exposed
homelab-ui's Kubernetes page and Headlamp need the Kubernetes API with full rights. Instead of giving a browser a token:
- `kube-api` runs `kubectl proxy` with a **cluster-admin** service account; the proxy adds the credentials.
- Its NetworkPolicy lets in **only Caddy and Headlamp**.
- Caddy's `/api/kube/*` and `:4466` require the `admin` role and `X-Homelab-Request` on writes, and drop the client's `Authorization` header.
The power is real, so it sits behind every layer at once.

## What's deliberately outside the sign-in
MongoDB `:27017` (its own password), Kafka `:9094` and OTLP `:4317/4318` (no auth), agent-runtime `:8000`, agent-toolbox `:8001`. Their clients are programs. They rely on the **network layer only** — tailnet devices. Known trade-off: any device on your tailnet can produce to Kafka. Tailscale ACLs could narrow it further.

## Known limits (honest list)
- **One node, one disk**: backups are on the same machine. A dead SSD loses both. An off-site copy is the missing piece.
- **Forced 90-day password expiry** is in the policy, though current NIST guidance advises *against* periodic forced changes (it pushes people to predictable passwords). Worth revisiting.
- **No MFA** on Keycloak yet: one password protects admin powers.
- **Tailnet = trust**: a stolen, signed-in laptop on your tailnet reaches the non-sign-in ports.
